# OFXPluginDeveloper - second Windows/CUDA field test

**Subject:** `cblinde/OFXPluginDeveloper` at `main`, cloned 2026-11-24
**Machine:** Windows 11 (10.0.26300), RTX 3060 (sm_86, driver 621.24 / CUDA UMD 13.5)
**Toolchain:** CUDA 13.0.48, MSVC 19.44.35224 (VS 18 BuildTools, `-vcvars_ver=14.44`),
MSVC 19.50 also present, CMake 4.4.4, Ninja 1.10.2, Git Bash (MSYS2)
**Scope:** re-run the documented Windows path end to end, on hardware, and fix what breaks.

Every command below was executed in a clone of this repository. Build trees and
the OpenFX FetchContent checkout stayed inside the project directory
(`templates/*/build/`, which `.gitignore` already covers) and were deleted before
committing. Nothing outside the project folder was written: no toolkit install,
no `pip`, no plugin installed into `%COMMONPROGRAMFILES%\OFX\Plugins`.

---

## 1. Verdict

The **reference material holds up**: pitch arithmetic, the CUDA/CPU split, the
stream policy, the visibility-and-export rules and the architecture-list fix all
survive a real toolkit, a real compiler and a real GPU. The kernels are bit-exact
on hardware, the bundle exports exactly two symbols, and the host-contract harness
passes every check against both templates.

The **verification plumbing still had three defects**, all of them in
`testkit/check-ofx-artifact.bat` / `build.bat`, and all of them of the same
family: a check that reports the wrong thing while the build says "success".
Two of the three made a *correct* build fail, and the third made a *CPU-only*
build assert CUDA device code it does not contain.

No defect was found in the plug-in sources, the CMake wiring, or `Kernel.cu`.

## 3. Findings and fixes

Severity: **S1** blocks the documented workflow, **S2** a wrong claim or a false
pass, **S3** polish.

### F1 - the artifact checker walks all of `C:\` (S1)

`testkit/check-ofx-artifact.bat` counted export rows with the legacy
`find /c /v ""`. Git-for-Windows ships **GNU** `find.exe` and puts `usr\bin`
ahead of `System32`, so the pipeline ran GNU find with `/c` as a path:

```
find: '/c/$Recycle.Bin/S-1-5-18': Permission denied         (4000+ lines, minutes)
```

The build had already linked successfully; it simply never returned, and the
first observation was the tool timing out. Only the export-count step is
affected, so the failure appears *after* a correct link, which is exactly where
a reader stops looking.

**Fixed:** every count uses `set /a` over a `for /f` loop, with no external tool.
The hazard is documented in the file header and in `BUILD_PLAYBOOK.md` §7.

### F2 - a loose regex counted dumpbin's header line as an export (S1)

With F1 fixed, the count became 3 for a DLL with exactly two exports:

```
FAIL: dumpbin reports 3 exported names, expected 2
    00000000 characteristics          <-- matches [0-9A-Fa-f]*: 'c' is a hex digit
          1    0 000105B0 OfxGetNumberOfPlugins
          2    1 000105D0 OfxGetPlugin
```

The same loose pattern was in the original one-liner, so this check had never
produced "2" on Windows; the 2026-11-22 report's export table (§5.3) was read by
hand, not by this script.

**Fixed:** the RVA is matched as eight explicit hex digits. Verified 2 for the
CUDA bundle, and the negative control still fails.

### F3 - a CPU-only build claimed device code it does not have (S2)

`build.bat` passed `--cuda` whether or not a CUDA path had been compiled, and the
checker counted every line of `cuobjdump -lelf` output as a cubin. For a binary
with no device code cuobjdump prints

```
cuobjdump info    : File '....ofx' does not contain device code
```

which counted as `device code: 1 cubin(s)`. So `CPU_ONLY=1 build.bat` passed a
check it should have failed, by believing a message that says the opposite.

**Fixed:** `--cuda` is passed only when a CUDA path was compiled, and the checker
counts only lines naming a `.cubin`. Verified: CUDA build 7 cubins, CPU-only
build no device-code line, `--cuda` on the CPU-only binary exits 1.

### F4 - `nvcc` needs `cl.exe`, which the documented recipe did not mention (S3)

The reproduction block in `FIELD_TEST_WINDOWS_CUDA.md` §8 ran `nvcc` from a plain
shell:

```
nvcc fatal   : Cannot find compiler 'cl.exe' in PATH
```

That is the first thing a reader hits when following the documented GPU check.

**Fixed:** the section now shows the `vcvars64.bat -vcvars_ver=14.44` call first,
and points at the new `test\run-tests.bat`, which enters the MSVC environment
itself.

### F5 - the CUDA template had no Windows test runner (S2, documentation gap)

`test/run-tests.sh` needs `g++`, `nm -D`, `readelf`, `dlopen` and valgrind; none
exists here. `TESTING_STRATEGY.md` and `SKILL.md` §10 therefore listed a
verification step that a Windows user could not perform, for the platform the
skill says it supports.

**Fixed:** `templates/minimal-cuda-ofx/test/run-tests.bat` runs the three checks
that have Windows equivalents - artifact (dumpbin/cuobjdump), the real GPU
harness, and the contract harness through `LoadLibraryExW` - and states which
Linux-only checks it does not replace.

### F6 - the reference template fails `--set gain=…`, confusingly (S3)

`ReferenceGain` multiplies all four channels; the harness's `--set` comparison
assumes an RGB-only gain and asserts alpha is unchanged. Nothing in the suite
passes `--set` for that plugin, so this surfaced only when run by hand, and the
message ("the plug-in ignored the parameter") pointed at the plug-in.

**Fixed:** the failure text now names the assumption and the flag
(`--set-status-only`). The plug-in's maths is unchanged.

## 4. What passed on real hardware

* **Kernels.** 28/28 launcher cases bit-exact against the CPU reference:
  padded and negative pitches, 4-byte-aligned bases (routed to the scalar
  kernel), window offsets inside bounds, 1x1 / 3x5 / 17x1 / 129x7 / 208x117,
  zero-size windows, overrun guards on every padding byte, host stream,
  default-stream completion, 8 concurrent host threads, zero-copy on pinned
  mapped memory, and both kernels launched directly.
* **Throughput** (1920x1080 RGBA32F, `cudaEvent`, 100 iterations, RTX 3060):
  vec4 0.219 ms/frame (~303 GB/s), scalar 0.242 ms (~274 GB/s). Bandwidth-bound
  on both paths; consistent with the 0.212/0.222 ms recorded in the 2026-11-22
  run, which remains the number quoted in the documents.
* **Artifact.** `dumpbin /exports` -> exactly `OfxGetNumberOfPlugins` and
  `OfxGetPlugin`; `cuobjdump -lelf` -> 7 cubins, `sm_75`...`sm_120`;
  `dumpbin /dependents` -> no CUDA runtime import (CUDA 13 on Windows resolves
  it at load), matching `SKILL.md` §6.
* **Host protocol.** 136 checks for the CUDA template (two load/unload cycles,
  four instances, three concurrent renders, byte-destination rejection,
  negative pitch, rejected out-of-bounds windows) and 110 for the reference
  template, 0 failures in both.
* **CPU-only path** builds under the Visual Studio generator and lands in
  `Contents\Win64` with no `/Release` subdirectory, so the `$<1:...>` output
  wrapper works for both generator families.

## 5. Limits of this run

* **No OFX host.** No Resolve, Nuke, SCRATCH or Natron on this machine, so no
  pixel was rendered by a host and `HOST_COMPATIBILITY_MATRIX.md` stays graded
  B/C. Plugin discovery, parameter UI and stream handling inside a real host
  remain unverified.
* **8/16-bit paths** are exercised only as *rejection*: both templates declare
  `eBitDepthFloat` and `render()` refuses a byte image (`--byte-dst-rejected`).
  There is no 8-bit or 16-bit implementation to test.
* **Single GPU**, so `DeviceGuard`'s save/restore is exercised on one device.
* **No sanitizer or memcheck pass on Windows**; `kernel_equivalence.cpp` does not
  compile under MSVC (`posix_memalign`), and the CPU emulation suite stays Linux-only.
* **`onnx-inference-ofx`** was not built here (no ONNX Runtime in this project).
* **`install-bundle`** was deliberately not run: it writes into
  `%COMMONPROGRAMFILES%\OFX\Plugins`, outside the project folder.
* Environment noise worth knowing: Microsoft's `vcvars64.bat` prints
  `Der Befehl "vswhere.exe" …` on this machine. It comes from the VS installer
  script (its `Installer` directory is not on this shell's `PATH`), not from this
  repository, and it is harmless - the scripts resolve `vswhere` by full path.

## 7. Host verification: the official host, and a real renderer

The contract harness proves the bundle honours OFX as this repository understands
it. It cannot prove that a host agrees. Two tiers were added and run here.

**Tier 1 - the OpenFX project's own host.** `testkit/official-host` builds
`HostSupport` (openfx 1.5.1) and its headless `cacheDemo` through FetchContent
(expat 2.6.4, static libraries). With `OFX_PLUGIN_PATH` pointing at the build:

| Observation | Value |
|---|---|
| plug-in found | `com.ofxplugindeveloper.minimalcudagain` |
| contexts | `OfxImageEffectContextFilter`, `General` |
| grouping | `OFX Plugin Developer` |
| render | `OfxImageEffectRenderInstanceSafe` |
| wall clock | 23 s, describing 84 plug-ins - the official cache appends the system plug-in directory after `OFX_PLUGIN_PATH` (`ofxhPluginCache.cpp:240`-`245`) |

**Tier 2 - NatronRenderer 2.5.0, headless.** 256x256 RGBA, one frame,
`ReadPNG -> plug-in (gain 0.5) -> WritePNG`:

| Observation | Value |
|---|---|
| exit status | 0 |
| geometry | 1920x1080 project, image inserted bottom-left, identical to the baseline |
| pixel (64,128,192,255) at gain 0.5 | (44,92,140), alpha 255 |
| expected | `srgb8(0.5 * linear(64,128,192))` = (44,92,140) |
| mismatch | none - delta 0-1/255 across 9 samples, alpha untouched |
| wall clock | 3.3 s |

The naive 8-bit expectation (32,64,96) is wrong: Natron colour-manages, so the
effect sees linear values and the writer re-encodes to sRGB. A linear gain of 0.5
maps 0.251/0.502/0.753 to 0.1746/0.3624/0.5506, i.e. (44,92,140). The check
compares against that formula rather than against an eyeballed number.

Negative controls: `--plugin-id com.ofxplugindeveloper.doesnotexist` fails with
`PLUGIN_NOT_REGISTERED` and exit 1; the plug-in-free baseline reproduces the input
exactly, so a wrong expectation cannot pass quietly.

Not covered, and not claimed here: a GUI host session, GPU rendering inside a host
(Natron renders on the CPU on this machine, which is why Tier 2 exercises the
fallback branch and not the device path), and Linux, which needs a second machine.
