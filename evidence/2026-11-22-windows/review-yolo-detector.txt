Feedback handover - OFXPluginDeveloper (third review)
Written 2026-11-22 while building com.ai.ofx.YoloObjectDetector from the skill.

Environment: Windows 11, no VS 2022 instance (VS 18 Build Tools, MSVC 14.50.35717),
CMake 4.4.4, Ninja 1.10, OpenFX OFX_Release_1.5.1, ONNX Runtime 1.20.1 (NuGet, CPU).
No OFX host and no macOS/Linux machine, so host behaviour and the Apple branches
are inferred, not measured.

Labels: [V] ran and pasted; [I] inferred from a header, packaging spec or platform
documentation.

Findings and where they were fixed
----------------------------------

F1 (high, macOS) - RPATH was "$ORIGIN" on every non-Windows platform;
dyld needs @loader_path and treats $ORIGIN as a literal directory.
  templates/onnx-inference-ofx/CMakeLists.txt (now APPLE / elseif(UNIX))
  templates/minimal-cuda-ofx/CMakeLists.txt (same split)
  [I] no Mac available.

F2 (high, macOS) - the runtime was copied as libonnxruntime.so.1 on macOS too;
the dylib's install name is @rpath/libonnxruntime.<version>.dylib.
  templates/onnx-inference-ofx/CMakeLists.txt: APPLE branch resolves the
  symlink (REALPATH) and keeps the versioned file name. [I]
  Documented in BUILD_PLAYBOOK.md section 7 and AI_MODEL_INTEGRATION.md section 4.

F3 (medium) - testkit could not declare a colour parameter: canonicalType()
mapped only double/int/string/bool, so --param boxColor:rgb failed although the
declared value was OfxParamTypeRGB [V, reproduced with the pre-fix harness].
  testkit/contract_main.cpp now maps rgb, rgba and choice; the vocabulary is
  listed in testkit/README.md.
  Post-fix verification [V]: a throwaway copy of templates/minimal-ofx declaring
  gain (double), boxColor (RGB), tint (RGBA) and mode (choice) was driven through
  testkit/contract_main.cpp with
  --param gain:double --param boxColor:rgb --param tint:rgba --param mode:choice
  -> "contract_test: 90 checks, 0 failed".

F4 (low) - SKILL.md section 6 named only Win64 / Linux-x86-64 / MacOS, while
BUILD_PLAYBOOK.md section 7 and ofxPackaging.rst:124 also have Linux-aarch64.
  SKILL.md now lists all four. [V] sources disagreed.

G1 (medium) - Support names for byte support were never stated:
OFX::eBitDepthUByte (there is no eBitDepthByte), and
bool getRegionOfDefinition(const RegionOfDefinitionArguments&, OfxRectD&)
(not OfxRectD getRegionOfDefinition(const Args&)).
  SKILL.md section 5 now has the depth table and the signature.

G2 (medium) - the ONNX template's runner is shape-preserving, but the routing
table did not say so: ModelRunner::Run requires out shape == in shape, so a
detection or classification head cannot use it.
  SKILL.md section 4 routing table row; AI_MODEL_INTEGRATION.md section 7 item 6;
  PATTERN_INDEX.md task row.

G3 (medium) - no guidance for drawing into the frame (destination pitch, bounds
vs render window, premultiplied overlay, bitmap font).
  ARCHITECTURE_AND_CUDA_PIPELINE.md section 13; PATTERN_INDEX.md task row.

G4 (medium) - no detection-model guidance (letterbox, [1, 4+N, anchors] layout,
per-class NMS, end-to-end exports).
  AI_MODEL_INTEGRATION.md section 7, "Detection heads: the four facts that cost
  a day".

P1 (low) - FetchContent_Populate() needed CMP0169 OLD on CMake >= 3.30.
  All three templates now use FetchContent_MakeAvailable() with
  SOURCE_SUBDIR cmake/do-not-build, and the policy escape is gone.
  Verified here [V]: minimal-ofx configured and built from a real network clone
  with no OFX_SOURCE_DIR (51 s configure), and all templates configured through
  MakeAvailable; ./run-tests.sh exit 0.

What worked and is now externally verified
------------------------------------------
- NuGet fallback is load-bearing: the GitHub release assets returned HTTP 404
  from that network for every version tried, while
  https://www.nuget.org/api/v2/package/Microsoft.ML.OnnxRuntime/1.20.1 returned
  200 (108 MB) and its layout (build/native/include,
  runtimes/win-x64/native/*.lib|*.dll) mapped onto <root>/include|lib|bin [V].
  Keep the section; consider the same treatment for the Linux tarball.
- Exactly two exports on MSVC [V]: dumpbin /exports on the built .ofx lists only
  OfxGetNumberOfPlugins and OfxGetPlugin, with no /EXPORT flags and only
  CXX_VISIBILITY_PRESET hidden (a documented no-op there).
- Bundle layout and arch names [V] for Win64; Linux-x86-64, MacOS and
  Linux-aarch64 match ofxPackaging.rst:81-124 (only SKILL.md section 6 was short).
- kOfxImagePropRowBytes is integer x 1, may be negative, not supported for
  OpenCL images [V] (ofxImageEffect.h:1340-1353).
- kOfxStatGPUOutOfMemory 1001 / kOfxStatGPURenderFailed 1002 [V]
  (ofxGPURender.h:185-189).
- testkit is genuinely reusable: unmodified, it drove a very different
  architecture (stateful detector behind a mutex, byte and float, RGB and RGBA,
  no image maths) through describe -> describeInContext -> createInstance ->
  isIdentity -> render -> destroyInstance -> unload, twice, with two live
  instances, four concurrent render threads and a negative-pitch destination:
  110 checks, 0 failed [V].
- BUILD_PLAYBOOK.md section 7 is accurate for the VS 18 machine: no VS 2022
  instance, vswhere -latest returns VS 18 BuildTools, the "Visual Studio 17
  2022" CMake generator cannot configure, and Ninja after vcvars64.bat worked
  first try [V].
- ORT version claims are consistent: PyPI reports 1.32.0, matching
  ORT_API_VERSION 32 in AI_MODEL_INTEGRATION.md section 4 [V]. This build used
  1.20.1 / API 20 for the NuGet reason above; nothing used differs.

Addendum, same report revised
-----------------------------
The handover was revised after the first round of fixes. Two items were new:

F3 (part 2, high) - the fake host could not READ a colour parameter either.
  paramGetValue/paramGetValueAtTime/paramSetValueAtTime handled double, integer,
  boolean and string only, so a plug-in reading kOfxParamTypeRGB got
  kOfxStatErrUnsupported from the host, Support turned that into an exception
  (ofxsParams.cpp:2228-2232), and the whole render action was reported as failed
  with no message naming the parameter [B].
  Fixed in testkit/fake_host.cpp: ParamObj stores 4 colour components, get/set
  return/set RGB (3) and RGBA (4), choice is an integer, FakeHost::setParam
  parses "r,g,b" / "r,g,b,a", and any still-unmodelled read or write records
  "fake host: read of parameter 'x' (Type) is not modelled" in messages().
  Verified here [V]: a copy of templates/minimal-ofx declaring gain, boxColor
  (RGB), tint (RGBA) and mode (choice), reading all three in render(), driven
  with --param ...:rgb/rgba/choice and
  --set gain=1.0 --set boxColor=0.25,0.5,0.75 --set tint=1,0.5,0.25,1 --set mode=1
  -> "contract_test: 136 checks, 0 failed".

F5 (medium) - OFX::Log::print is silent in Release builds. Support opens the log
  file only inside #ifdef DEBUG (ofxsLog.cpp:40-47), so every "log the error"
  recipe in the skill produced nothing in the build a user runs [V]. A review
  pass here added the sharper fact: CMake's Debug configuration does not define
  DEBUG either, so the call writes nothing in any build without -DDEBUG.
  Fixed as documentation: SKILL.md (Phase 8 and section 7),
  ARCHITECTURE_AND_CUDA_PIPELINE.md (logging), REFERENCE_READING_GUIDE.md and
  BEST_PRACTICES_AND_PERFORMANCE.md 5.7 now state the DEBUG-only behaviour and
  point at OFX::ImageEffect::setPersistentMessage (ofxsImageEffect.h:1067) for a
  message the host shows; they also note that it needs message suite v2.

Also kept from the first revision: the -Wall -Wextra fixture build and the
documented vocabulary in testkit/README.md.

F6 (high, crash) - the ONNX template's Windows bundle crashed in Resolve.
  It linked onnxruntime.lib and copied the DLL as onnxruntime.dll. Windows
  resolves an import by module base name and searches the executable's directory
  first, so Resolve's own onnxruntime.dll (1.13, beside Resolve.exe) was bound
  instead of the bundled 1.20: GetApi(ORT_API_VERSION=20) returned null, the C++
  wrapper stored it unchecked, and the first ORT call access-violated inside
  render. Resolve's minidump names the host's DLL; the bundle's file never
  appears in the module list [B]. The same applies to Windows ML's copy in
  System32, so "works on my machine" proves nothing.
  Fixed in templates/onnx-inference-ofx:
    - CMake on WIN32 no longer links the import library, and compiles both the
      plug-in and ai_pipeline_test with ORT_API_MANUAL_INIT;
    - the bundle and the test directory carry the runtime as
      onnxruntime-ofx.dll (build.bat asserts that name);
    - ModelRunner loads the private name from the module directory with
      LoadLibraryExW(LOAD_LIBRARY_SEARCH_DLL_LOAD_DIR |
      LOAD_LIBRARY_SEARCH_DEFAULT_DIRS), resolves OrtGetApiBase, calls
      GetApi(ORT_API_VERSION), checks for null, calls Ort::InitApi(api), and
      never calls FreeLibrary. A missing or too-old runtime throws from
      ModelRunner (a render error with a message) rather than crashing.
    - AI_MODEL_INTEGRATION.md section 4, BUILD_PLAYBOOK.md section 7,
      PATTERN_INDEX.md and SKILL.md carry the rule.
  Verification here is partial by nature: the Linux build and all suites still
  pass with the unchanged static linking, and the new Windows code type-checks
  against the real ORT 1.20 headers with a stub windows.h (-Wall -Wextra,
  -fsyntax-only). It cannot be compiled with MSVC or executed here, so the
  loader and the CMake branch remain [I] until a Windows run repeats the field
  test. The
  referenced field evidence for the failure itself is [B].

Addendum 2 (2026-11-22, F7 and F8)
----------------------------------
Same session, later. Two more harness holes and one bug that reached a user.

F7 (high) - a kOfxParamTypeChoice knob declared fine but could not be read or
set: paramGetValueAtTime returned kOfxStatErrUnsupported for it, Support threw,
and render failed after describe/createInstance with no message. FakeHost::setParam
refused a choice for the same reason, and the declared option list could not be
read back.
  Fixed: choice shares the integer path in all four get/set functions and in
  setParam; FakeHost::paramOptions(name) returns kOfxParamPropChoiceOption in
  order, so a test can assert what the dropdown offers. [V] here: it compiles and
  the contract suites still pass; the reporter measured 32/32 on their fixture [B].

F8 (high, shipped) - OFX images are y-up: kOfxImagePropData addresses the row at
bounds.y1. A plug-in that drew labels and plates assuming the pointer was the top
row produced a mirrored overlay in Resolve 21 (1088x832, float RGBA, pitch 17408
positive), while the harness stayed green: every check compared destination to
source row for row through the same pointer, and a copy is orientation-agnostic.
  Root cause of the blind spot: the fake host derived the pointer's origin from
  the stride sign, so the layout that makes a mirror-blind plug-in look right -
  top-down data with bounds still starting at y1 - could not be built.
  Fixed in the testkit: setImageOrigin(ImageOrigin::Bottom|Top) and
  setNegativePitch are separate axes; all four layouts are in-buffer, the default
  is Bottom+positive (Resolve's layout), and --image-origin top|bottom selects it
  from the CLI.
  Documented in SKILL.md rule 3 and section 8, AI_MODEL_INTEGRATION.md section 5,
  PATTERN_INDEX.md and testkit/README.md (layout table and what each one proves).
  The plug-in-side fix (rebase to data + (h-1)*rowBytes with a negated stride, and
  take the view's size from the render window rather than the image bounds) and
  its 94-check tile_window_test are [B]: they live in the reporter's tree, not
  here. No drawing plug-in exists in this repository, so the four layouts are
  constructible but only a plug-in that draws at chosen positions can assert
  orientation.

Also reported, already covered: the NuGet package as fallback when the GitHub
release assets 404 (AI_MODEL_INTEGRATION.md section 4), exactly two exports under
MSVC, and the GPU status codes. One addition made here: the Linux tarball has a
mirror route too (pip download for the library, headers from the same tag).

Addendum 3 (2026-11-22, F9 to F15)
----------------------------------
The same session's later passes, while the detector grew an open-vocabulary model,
a help page, a push button and a promptable export. Seven findings, none of which
a build or the existing suites could see.

F9 (high) - class names came from coco_classes.hpp, not from the model. A
YOLO-World v2 export with 35 baked terms labelled the bus "frisbee": class 29 of
that vocabulary was answered with COCO's thirtieth name. The larger half is
older than the model - every model opened through the documented "Custom path"
feature was labelled with COCO names, so an advertised feature mislabels its
output. Ultralytics writes custom_metadata_map["names"], a Python dict literal;
the fix reads it at session creation, keeps the side-car file as the override,
and only falls back to COCO when the graph carries no names. The parser has to
accept the writer's sloppiness (quotes, bare or quoted numeric keys, a plain
list) and reject sparse or negative indices [B]. Documented in
AI_MODEL_INTEGRATION.md section 7, "Detection heads".

F10 (low) - contract_test's --set assumed a gain: it compared the frame with
src * atof(value), so fontScale=2.5 failed with "max deviation 1.125" and
classFilter=person with 0.75, although the plug-in was right [B]. Fixed with
--set-status-only, which renders, asserts kOfxStatOK and the accepted write and
skips the comparison; the usage text and testkit/README.md now state the
assumption next to the flag.

F11 (medium, export) - YOLOE's head bakes the class count at trace time
(int(x[-1].shape[1])), so a graph traced with three classes fails with any other
count ("Non concat axis dimensions must match ... 25200 and 8400", then a
Reshape), and CLIP appends </w> before the merges, so person</w> (2533) and
person (3510) both exist and a tokenizer that skips the marker is one token off
for every single-word prompt. The embeddings stay near 0.96 cosine either way,
so only an id comparison catches it [B]. Documented in AI_MODEL_INTEGRATION.md
section 7.

F12 (high, crash) - an Ort::Env in a function-local static was destroyed at
DLL_PROCESS_DETACH, after the runtime had begun shutting down: "221 checks, 0
failed", "ok 221 - kOfxActionUnload", then exit 139 - 0 once and 139 nine times
with the same binary [B]. Fixed in templates/onnx-inference-ofx/src/ModelRunner.cpp
by leaking one new Ort::Env per process; AI_MODEL_INTEGRATION.md section 4 states
the rule for env, session and thread-pool objects.

F13 (medium) - the fake host's paramSetValue/paramSetValueAtTime read scalar
arguments as pointers (*va_arg(ap, double*)), but OFX passes them by value. The
first setValueAtTime from a plug-in read address 0x3FF0000000000000 and crashed
inside the host with the stack pointing at the plug-in. Push buttons had no click
path at all, and mainEntry's kOfxStatReplyDefault looked like a failure [B].
Fixed here: both setters read double/int by value; FakeHost::setParam now calls
paramSetValueAtTime instead of writing the fields, so every template's --set test
exercises the convention; FakeHost::pressParam sends kOfxActionInstanceChanged
with kOfxPropType, kOfxPropName, kOfxChangeUserEdited, the time and the render
scale, and counts only kOfxStatFailed/kOfxStatErrBadHandle as a rejection.
Verified here [V] with a fixture plug-in that declares an integer and a push
button and writes 7 through paramSetValueAtTime on the click: set->3, press->7.

F14 (medium) - nothing in the build guidance asked whether the licence texts of
bundled models, fonts and tokenizer tables travel in the bundle. The ledger sat
in the repository root while the installed bundle carried 385 MB of AGPL-3.0 and
research-only weights [B]. SKILL.md section 6 and BUILD_PLAYBOOK.md section 3.11
now say: POST_BUILD + copy_if_different (after the asset copies, before stale
cleanup), warn instead of fail when the file is missing.

F15 (medium) - a text overlay cannot be judged at 320x240, and "the frame
changed" passes for a page drawn upside down or clipped past the column edge.
The reporting tree found both with a host-free 12-check test at 1280x720,
640x480 and 320x240 that asserts bounds (ink inside the panel, both columns,
nothing past the right edge) and dumps a PPM; the OFX suites had been green [B].
TESTING_STRATEGY.md section 5 and section 14 now state that layout is a bound and
point at contract_test --size WxH, which already existed.

What was not verified here: the promptable export, the metadata parser, the
full-page overlay and the licence copy step live in or came from the reporter's
tree. This checkout changed the harness, the ONNX template's environment and the
documentation, and ./run-tests.sh plus the fixture above cover those.
