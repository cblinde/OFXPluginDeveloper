# OFXPluginDeveloper — field test report

**Subject:** `cblinde/OFXPluginDeveloper` (commit at `main`, cloned 2026‑11‑22)
**Tested by:** automated agent session, at the request of the repository author's environment owner
**Machine:** Windows 11 (10.0.26300), RTX 3060 (sm_86), driver 621.24 / CUDA UMD 13.5
**Date:** 2026‑11‑22

---

## 1. Verdict in one paragraph

The **reference material is accurate and unusually good**: every constant, header quirk
and ground rule this test could check held up, and the template's design (CPU/CUDA split,
pitch arithmetic, stream policy, visibility) survived real hardware and a real Windows
toolchain. The **build and test plumbing does not survive Windows**, which is the one
platform the skill says it supports and simultaneously admits it never executed:
`build.bat` failed on first run at four consecutive, independent points, and after the
build finally succeeded it produced a bundle in the **wrong architecture directory while
reporting success**. The CPU-emulated test suite and the `dlopen` contract harness cannot
run on Windows at all (no `g++`, `nm -D`, `readelf`, `valgrind`, `dlopen`). On the
positive side, after the fixes below, the Windows `.ofx` passes **74/74 host-contract
checks** and the kernels pass **28/28 real-GPU cases bit-exactly**, which are two things
the repository has never had before.

Every defect listed in §4 was reproduced, diagnosed to a file and line, fixed in place,
and re-verified. The fixes are in the working tree; §9 lists them as a patch.

Severity legend: **S1** = blocks the documented workflow; **S2** = silently wrong output
or wrong claim; **S3** = documentation/polish.

## 4. Findings

### F1 — `build.bat` hard-codes a generator that may not exist (S1)

```
cmake -S "%HERE%." -B "%BUILD_DIR%" -G "Visual Studio 17 2022" -A x64 %EXTRA%
```
On this machine the only Visual Studio instance **with a C++ toolset** is 2026; the 2022
Build Tools are installed without `VC/Tools/MSVC`. First real run of the script:

```
CMake Error at CMakeLists.txt:3 (project):
  Generator
    Visual Studio 17 2022
  could not find any instance of Visual Studio.
BUILD FAILED (see the cmake output above)
```

This is the first thing a Windows user with a clean, current Visual Studio install sees,
and the message names nothing actionable. It is also the exact failure the README's
"Known gaps" predicted ("`build.bat` has never been executed").

**Fixed:** the generator is resolved through `vswhere -latest -products *
-requires Microsoft.VisualStudio.Component.VC.Tools.x86.x64`, mapping the major version
to the CMake generator name, with `CMAKE_GENERATOR` as the override. Verified: the run
now prints `[build] generator: Visual Studio 18 2026`.

---

### F2 — Unquoted `-D` values split at the space in "Program Files" (S1)

```
if not defined CUDA_FOUND set "EXTRA=%EXTRA% -DCMAKE_CUDA_COMPILER=%CUDA_FOUND%\bin\nvcc.exe -DCUDAToolkit_ROOT=%CUDA_FOUND% ..."
```
`%CUDA_FOUND%` is `C:\Program Files\NVIDIA GPU Computing Toolkit\CUDA\v13.0`, so CMake
received `-DCUDAToolkit_ROOT=C:\Program` plus a stray argument:

```
[build] CUDA toolkit: C:\Program Files\NVIDIA GPU Computing Toolkit\CUDA\v13.0\bin\..
CMake Warning:
  Ignoring extra path from command line:
   "Toolkit\CUDA\v13.0\bin\.."
```

Two bugs in one line: the value is unquoted, **and** the discovery leaves the path
un-normalised (`...\v13.0\bin\..`), which is what makes the stray token look like a path
rather than a variable expansion bug.

**Fixed:** discovery canonicalises through `for %%J in ("%%~dpI..") do set "CUDA_FOUND=%%~fJ"`,
and every `-D` is quoted. The leftover `Linux-x86-64` artefact from the un-normalised
path is also gone.

### F3 — Visual Studio generators cannot compile CUDA without NVIDIA's build customisations (S1)

With the generator fixed, the next stop:

```
CMake Error at .../CMakeDetermineCompilerId.cmake:714 (message):
  No CUDA toolset found.
```

A VS generator compiles `.cu` only through NVIDIA's MSBuild `BuildCustomizations` for
*that exact VS version*. CUDA 13.0 ships none for VS 2026, so the VS path is dead on any
machine without NVIDIA's matching VS integration — and CMake's message does not say so.
The skill never mentions this coupling; `SKILL.md` §6's "MSVC" paragraph talks only about
`/MD` vs `/MDd`.

**Fixed:** `build.bat` probes `%VSINSTALL%\MSBuild\Microsoft\VC\*\BuildCustomizations\CUDA *.props`
and falls back to **Ninja + `vcvars64.bat`** when the customisations are missing, printing
why. Verified: `[build] generator: Ninja (no NVIDIA build customisations for the installed Visual Studio)`.

### F4 — `nvcc` 13.0 rejects MSVC 19.50 (VS 2026) outright (S1)

Independently of the generator, with the VS toolset selected:

```
C:\Program Files\NVIDIA GPU Computing Toolkit\CUDA\v13.0\include\crt/host_config.h(164):
fatal error C1189: #error:  -- unsupported Microsoft Visual Studio version!
Only the versions between 2019 and 2022 (inclusive) are supported!
The nvcc flag '-allow-unsupported-compiler' can be used to override this version check
```

This is a **toolkit/MSVC version matrix** problem the skill has no section for. It will
hit anybody who installs "the newest Visual Studio" and "the newest CUDA", which is the
default outcome of following both download links.

**Fixed (in the Ninja path only):** the fallback calls
`vcvars64.bat -vcvars_ver=14.44` — the newest MSVC that `host_config.h` accepts — and
echoes the `cl` version so the log shows what was used. Verified: `cl` 19.44.35224,
`Kernel.cu` then compiles.

**Documentation needed (not fixed, needs your decision):** the skill should carry an
explicit compatibility row — *CUDA 12.x/13.0 support MSVC ≤ 19.44; VS 2026's 19.50 needs
`-allow-unsupported-compiler`, and `build.bat`'s toolset pinning is the safer route.*

### F5 — The Windows build wrote the `.ofx` into `Contents/Linux-x86-64/` and reported success (S2 → would be S1 in a host)

After F1–F4 the build completed:

```
[11/11] Linking CXX shared module bundle\MinimalCudaGain.ofx.bundle\Contents\Linux-x86-64\MinimalCudaGain.ofx
Bundle: ...\bundle\MinimalCudaGain.ofx.bundle
  CUDA path: compiled in, links cudart64_*.dll
```

The last two lines *claim* a Win64 bundle. The file is in the Linux directory:

```
find build/bundle -name '*.ofx'
  .../Contents/Linux-x86-64/MinimalCudaGain.ofx      <-- only file produced
```

Cause: `CMakeLists.txt` sets `LIBRARY_OUTPUT_DIRECTORY` to `.../Linux-x86-64` and
`RUNTIME_OUTPUT_DIRECTORY` to `.../Win64`. Which one a `MODULE` target uses depends on
platform **and generator**: MSVC multi-config generators use `RUNTIME_`, Ninja on
Windows uses `LIBRARY_`. So the bundle layout is correct only for the generator the
author happened to use on Linux.

This is the worst class of bug in the repository's own terms: a build that reports
success and produces an artefact no host will scan, with no error anywhere.

**Fixed** in both templates: the arch directory is chosen from `WIN32`/`APPLE`, both
output properties point at it, and each is wrapped in `$<1:...>` so multi-config
generators do not append `/Release`:

```cmake
if(WIN32)      set(_ofx_arch_dir "Win64")
elseif(APPLE)  set(_ofx_arch_dir "MacOS")
else()         set(_ofx_arch_dir "Linux-x86-64")
endif()
set(_ofx_bundle_arch_dir ".../Contents/${_ofx_arch_dir}")
set_target_properties(... LIBRARY_OUTPUT_DIRECTORY "$<1:${_ofx_bundle_arch_dir}>"
                          RUNTIME_OUTPUT_DIRECTORY "$<1:${_ofx_bundle_arch_dir}>")
```

Verified: `find build/bundle -name '*.ofx'` → `Contents/Win64/MinimalCudaGain.ofx`.

### F6 — Second run in the same build directory is a dead end (S1)

Because the script can choose different generators on different runs (Ninja for CUDA, VS
for CPU-only), the second run dies with:

```
CMake Error: Error: generator : Visual Studio 18 2026
Does not match the generator used previously: Ninja
```

No hint that deleting `build\` is the fix.

**Fixed:** `build.bat` reads `CMAKE_GENERATOR:INTERNAL` from `build\CMakeCache.txt` and
reuses it (`[build] reusing generator from build\CMakeCache.txt: ...`), and refuses
loudly, with instructions, if the cached generator cannot compile CUDA.

### F7 — The curated CUDA architecture list collapses to one architecture on every re-configure (S2)

`SKILL.md` §6 documents this trap and claims the template avoids it by capturing
`CMAKE_CUDA_ARCHITECTURES` *before* `enable_language(CUDA)`. That works for the **first**
configure and fails for every one after it, because `enable_language()` stores the
compiler default in the **cache**. Measured, second configure of the same tree:

```
-- CUDA architectures: 75
```
and `build.ninja` carried a single `--generate-code=arch=compute_75`.
A clean configure produced seven. So an incremental rebuild silently dropped 80/86/89/90/100/120
— the same failure the comment says it prevents, just delayed by one configure.

Impact: the shipped binary JIT-compiles on Ampere/Ada/Hopper/Blackwell instead of using
SASS, and `SKILL.md`'s "A bare number emits SASS **and** PTX" promise is only true for a
pristine tree.

**Fixed** by recording nvcc's default once and treating `CMAKE_CUDA_ARCHITECTURES` as a
user choice only when it differs from that default:

```cmake
if(NOT DEFINED OFXPLUGIN_COMPILER_DEFAULT_ARCHS)
  set(OFXPLUGIN_COMPILER_DEFAULT_ARCHS "${CMAKE_CUDA_ARCHITECTURES}" CACHE INTERNAL ...)
endif()
...
if(OFXPLUGIN_USER_CUDA_ARCHS AND NOT "${OFXPLUGIN_USER_CUDA_ARCHS}" STREQUAL "${OFXPLUGIN_COMPILER_DEFAULT_ARCHS}")
```

Verified three ways: clean configure prints the 7‑arch list; the **second** configure
keeps it (`grep -c -- --generate-code` = 7); `cuobjdump -lelf` on the finished `.ofx`
lists `sm_75, sm_80, sm_86, sm_89, sm_90, sm_100, sm_120`.

### F8 — `build.bat` prints a CUDA linkage claim that is false on Windows (S3)

```
echo   CUDA path: compiled in, links cudart64_*.dll
```
The produced `.ofx` has **no CUDA runtime import**:

```
dumpbin /dependents → KERNEL32, MSVCP140, VCRUNTIME140, VCRUNTIME140_1, api-ms-win-crt-*
```
and the only related string in the image is `cudart_hybrid64.dll`. The device code is
definitely present (`cuobjdump -lelf` lists 7 cubins; `cudaPointerGetAttributes` is
referenced from `Kernel.cu.obj`), and `LoadLibrary` succeeds, so nothing is broken — but
CUDA 13's Windows runtime no longer produces the loader-level `cudart64_*.dll` dependency
that `SKILL.md` §6 ("Depends on `cudart64_*.dll` / `libcudart.so.*` at load") and the
script's own output describe.

**Not fixed** — this needs your knowledge of CUDA 13's hybrid runtime rather than a guess.
Suggest: change the message to report what was measured (`dumpbin /dependents`) instead of
what was intended, and add a note to the runtime-linkage table.

### F9 — The contract harness could not run on Windows, by its own admission (S1)

```cpp
// Linux/macOS use dlopen/dlsym. On Windows the equivalent is LoadLibraryExW +
// GetProcAddress on the same two names; that path is documented in
// TESTING_STRATEGY.md but not built here.
#include <dlfcn.h>
```

So L1/L3 — the layer that proves the artefact is loadable and honours the host contract —
was Linux-only, for a skill whose stated scope is "Linux or Windows".

**Fixed:** `contract_main.cpp` now has a real `_WIN32` path
(`MultiByteToWideChar` + `LoadLibraryExW(..., LOAD_WITH_ALTERED_SEARCH_PATH)` +
`GetProcAddress`, `FreeLibrary`, and `FormatMessage`-based error text), and
`testkit/build-contract-test.bat` compiles it with MSVC. Verified: **74 checks, 0 failed**
against the Windows bundle, including `--negative-pitch`, `--byte-dst-rejected` and the
double open/unload cycle.

The comment is worth keeping in spirit: the `#ifdef` belongs exactly there, in one
translation unit, not in a second copy of the checks.

### F10 — The rest of the test layer is unrunnable on Windows (S1, documentation gap)

`templates/minimal-cuda-ofx/test/run-tests.sh` requires `g++`, `nm -D`, `readelf` and
`valgrind`; `kernel_equivalence.cpp` calls `posix_memalign` (4 sites), which MSVC does not
have. None of those tools exists on this machine. `BUILD_PLAYBOOK.md`'s "measured contract
(`nm`, `readelf`, `dlopen`)" is therefore a Linux-only contract with no Windows
equivalent, and `SKILL.md` §10's checklist ("`nm -D` shows only the two entry points")
cannot be followed by a Windows user.

Two additions would close this and are cheap:

* a `dumpbin /exports` equivalent of the `nm` check (2 exports — verified, §5.3);
* `cuobjdump -lelf` as the Windows equivalent of `readelf -S | grep nv_fatbin`
  (7 cubins — verified, §5.3).

Both are in the patch as helper scripts; they are not yet wired into `run-tests.sh`.

```bash
if [[ -z "${ONNXRUNTIME_ROOT:-}" ]]; then
  echo "error: ONNXRUNTIME_ROOT is not set; the ONNX template cannot build." >&2

```
The repository's "one command for the whole host-side test story" exits **before building

### F12 — `minimal-ofx` (the "reference plug-in") had no Windows build path (S2, fixed)

`templates/minimal-ofx/` ships `build.sh` and `exports.map` only. `exports.map` is a GNU
version script and is correctly guarded with `if(UNIX AND NOT APPLE)`, so on Windows the
export set is whatever `__declspec(dllexport)` provides — which is correct (exactly two),
but unreachable by the documented one command. It also had the same wrong-arch-directory
bug as F5, so even a hand-rolled Windows build produced
`Contents/Linux-x86-64/ReferenceGain.ofx`.

**Fixed:** the arch-directory block, and a `templates/minimal-ofx/build.bat` that mirrors
the CUDA template's generator handling (vswhere → newest instance with the C++ toolset,
`CMAKE_GENERATOR` override, reuse of the generator cached in `build\CMakeCache.txt`,
Ninja branch that calls `vcvars64.bat` first). It has no CUDA discovery because this
template has no CUDA path, and no toolset pinning because that is an nvcc constraint.

It also ends with a check the Linux script does not need and this platform does: the
assertion that the `.ofx` really is at `Contents\Win64\`. That single check is what turns
F5 from a silent wrong bundle into a failed build. Exercised both ways — with the F5
output-directory defect reintroduced in a scratch copy, the script exits 1:

```
BUILD FAILED: no .ofx in Contents\Win64
  expected: ...\Contents\Win64\ReferenceGain.ofx
  produced:
...\Contents\Linux-x86-64\Release\ReferenceGain.ofx
```

(The produced path also shows the multi-config `/Release` suffix that the `$<1:...>`
wrapper removes — the second half of F5, visible in the same line.)

### F13 — `test/gpu-kernel-test.cu` (new): the repository's first hardware test

`SKILL.md` §12 is honest that no kernel has ever executed on hardware, and
`TESTING_STRATEGY.md` explains why the CPU-emulated harness is believed sufficient. On a
machine with a GPU, it is not sufficient, and two things the emulation cannot see showed
up immediately (both in my own harness, both worth adding to the skill's rules):

1. **A host-supplied stream is not ordered against the legacy default stream.** The first
   version uploaded the source with `cudaMemcpy` and launched on a `cudaStreamNonBlocking`
   stream; 2 of 28 cases failed at a mid-image row because blocks read half-written
   source. Emulation cannot catch this. Proposed new ground rule: *"`cudaMemcpy` on the
   default stream does not order against a non-default stream; if the host gave you a
   stream, every transfer you make must be on that stream."*
2. **The vec4 path is not measurably faster at 1080p** — see §5.2. The PTX-count
   assertion ("1 load + 1 store") is a correctness property, not a performance one.

The harness is in the patch as `templates/minimal-cuda-ofx/test/gpu-kernel-test.cu`
(standalone: `nvcc -arch=sm_86 test/gpu-kernel-test.cu -o gpu-kernel-test.exe`).

## 5. What passed — claims now verified on real hardware

### 5.1 Kernel correctness on hardware (new)

`test/gpu-kernel-test.cu`, RTX 3060 (sm_86), CUDA 13.0 compiler, CUDA 13.5 driver runtime:

```
device 0: NVIDIA GeForce RTX 3060, compute capability 8.6, 28 SMs, 12287 MiB
runtime : CUDA 13.5 (13050), unified addressing yes, host-mapped yes
[1/6] geometry, pitch and routing through the launcher
[2/6] stream semantics
  200 queued launches on one non-blocking stream, one sync: ok
[3/6] concurrent launches from host threads
  8 threads, 0 failing
[4/6] zero-copy on host-mapped memory
  128x64 on pinned mapped memory, no device allocation: ok
[5/6] both kernels launched directly (bypassing the launcher)
  vec4 (direct)   333x101 exact match
  scalar (direct) 333x101 exact match
[6/6] throughput ...
28 launcher cases, 0 failure(s)
PASS: hardware matches the CPU reference bit for bit
```

Cases covered, all bit-exact against a host reference using the same pitch arithmetic:

* packed 64×48, padded pitch (+256), pitch +8 (not 16-aligned → scalar path);
* base pointer +4 bytes (float4 would fault — routing picks the scalar kernel, confirmed
  against `IsVec4Addressable`);
* window offset inside bounds (the `window.x1- bounds.x1` origin arithmetic in `Plugin.cpp`);
* negative pitch, both 16-aligned (vec4) and not (scalar) — the flipped-image case;
* 1×1, 3×5, 17×1, 1×17, 63×65, 16×16, 32×33, 129×7, **208×117** (the thumbnail arithmetic
  `SKILL.md` cites), 0-width and 0-height (must be a no-op);
* overrun: every byte outside the render window and every padding byte asserted unwritten;
* `WaitForDefaultStream()` completion path and the host-stream path.

This is the first time `SKILL.md`'s claim "the vectorized kernel emits one 16-byte load and
one 16-byte store per pixel" has been observed to produce correct pixels rather than
correct PTX.

### 5.2 Throughput (first real numbers in the repository)

1920×1080 RGBA32F, 100 iterations, `cudaEvent` timing, RTX 3060:

| Kernel | ms/frame | Effective bandwidth |
|---|---|---|
| vec4 | 0.212 | 312 GB/s |
| scalar | 0.222 | 300 GB/s |

~4% difference on a ~360 GB/s card — i.e. both paths are bandwidth-bound and the
vectorisation is **not** the performance lever the PTX section implies. Worth stating
explicitly in `BEST_PRACTICES_AND_PERFORMANCE.md`, because a reader currently concludes
that the `float4` path is where the speed is.

## 7. Not verified / limitations of this report

* **No OFX host.** DaVinci Resolve, Nuke, SCRATCH and Natron are not installed on this
  machine, so nothing here says a pixel was rendered by a host. `HOST_COMPATIBILITY_MATRIX.md`
  stays graded B/C.
* **Single GPU**, so multi-GPU `DeviceGuard` behaviour is untested beyond the code path
  being exercised (one device).
* **No sanitizer/valgrind pass on Windows.** MSVC has no ASan equivalent here that the
  scripts use, and `kernel_equivalence.cpp` does not compile under MSVC (`posix_memalign`).
* **Performance is one GPU, one resolution, one kernel.** No Nsight capture.
* **`onnx-inference-ofx`** was not built (no ONNX Runtime), so its Windows story is unknown.
* **Install target** was not exercised into a system plugin directory (deliberately: this
  test was required to leave the machine outside the project untouched). `install-bundle`
  itself is a `cmake -E copy_directory` into `OFX_INSTALL_DIR` and was not run.
* Fixes are **uncommitted** local edits. `SKILL.md` §11 mandates commit+push per change;
  that was not done because pushing to your repository is not authorized here.
